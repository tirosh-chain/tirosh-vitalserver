# Canonical Vital v3 artifact is misindexed by a fixed-offset parser

> ID: TS-168
> Category: Vital Files / Guest containers / TestKit
> Owner: Vital File compatibility
> Status: active

## Symptoms

A newly generated `.vital` file opens with Python `vitaldb`, but bundled
VitalServer indexing or browser preview reports an empty/corrupt file, an
incorrect time range, or invalid packet types. Rewriting the same artifact to a
10-byte header can appear to make it work.

The decompressed file identifies canonical v3 output:

```text
magic=VITA
version=3
headerLength=27
packetOffset=37
```

## Impact

Canonical artifacts generated by TestKit or Recorder Recovery may not appear in
the VitalServer library or preview even though the artifact itself is valid.
Downgrading the artifact hides the parser defect and discards current header
metadata.

## Cause

The bundled server index reader and browser webview reader started packet
parsing at byte `20`. Byte `20` is correct only when `headerLength=10` because a
Vital packet stream starts at `10 + headerLength`.

The previous exporters compensated by deleting the v3 time/packed fields and
rewriting `headerLength=10`. That made writer output depend on one legacy
consumer and prevented new artifacts from remaining canonical v3.

## Checks

Inspect the decompressed prefix without changing the file:

```python
import gzip
from pathlib import Path

payload = gzip.decompress(Path("case.vital").read_bytes())
print(payload[:4])
print(int.from_bytes(payload[4:8], "little"))
header_length = int.from_bytes(payload[8:10], "little")
print(header_length, 10 + header_length)
```

Valid supported inputs declare version 1, 2, or 3. Unknown future versions must
be rejected; they must not be parsed with a guessed offset.

## Actions

Use a Runtime image containing the maintained VitalServer runtime patches. The
server index module and served webview script validate versions 1/2/3 and derive
both packet passes from `10 + headerLength`.

Do not rewrite a v3 artifact to a 10-byte header. TestKit and Recorder Recovery
now use the shared canonical writer, which writes v3 and verifies the resulting
header and track kinds by reading the artifact back.

## Prevention

- Version/header probing is shared by Lab, TestKit, and the writer verifier.
- The runtime patch fails startup/asset delivery when its upstream anchor no
  longer matches instead of silently serving an unpatched parser.
- Tests apply patches to the actual bundled upstream assets.
- The streaming index test forces a 65,535-byte declared header across gzip
  output chunks so the first chunk cannot be mistaken for the complete header.
- Artifact tests require `version=3`, `headerLength=27`, and dynamic packet
  offsets.

## Operational Notes

The source file does not need deletion or regeneration when it is already valid
v3. Deploy the corrected parser and re-run indexing/upload. Existing v1/v2 files
remain accepted as input.

- 2026-07-21: shared v3 writer and header-length runtime patches implemented;

  maximum-length extension-header fixtures. The actual Docker HTTP response for
  `/static/js/webview.js` contains both dynamic-offset passes and version
  validation. An end-to-end file parse/draw browser smoke remains a release
  validation item.
