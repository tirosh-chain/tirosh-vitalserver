# Contracts

This directory owns language-neutral, versioned API, event, command, state, and receipt definitions shared across deployable units.

## Canonical sources

- `json-schema/v1/` contains JSON Schema Draft 2020-12 documents. Every persisted or cross-process document has an explicit `schemaVersion` and a stable URN `$id`.
- `openapi/control.v1.json` describes the public Control API major. It references the JSON Schema source; it is not a second model.
- `catalog/v1.json` maps each contract to its owner, boundary, and every canonical schema source.
- `policies/v1/` contains executable cross-owner contract rules, such as the allowed `Operation` transition graph. A service implements its own pure domain policy later; it must conform to this graph.
- `examples/v1/` contains positive and negative decode evidence. No example contains secrets, patient identifiers, waveform values, or raw recorder payloads.
- `compatibility/v1/baseline.json` is a generated, frozen baseline used to reject breaking changes within the `v1` major. New v1 contracts are added only with an explicit compatible extension; an existing baseline cannot be silently regenerated.

## Contract rules

1. `apiVersion`, persisted `schemaVersion`, recorder `protocolVersion`, and provider capability revision are different version axes.
2. `ReadResult` keeps `missing`, `invalid`, `unavailable`, `failed`, `stale`, `empty`, and `unsupported` distinct. None may be formatted or decoded as `available`.
3. `CommandRejection` means the owner did not admit a command and no `Operation` exists. It covers invalid input, revision conflict, and a dependency failure known before forwarding. `CommandAdmissionFailure` preserves the distinct case where admission is unknown; clients retry the exact `requestId` only after the owner recovers. A command admitted for execution returns an `Operation`; an observed execution failure is represented by terminal `Operation.state=failed`.
4. `RuntimeTopology.spec` contains references only. It must never contain endpoint credentials or secret material.
5. Receipt contracts separate ingress durability, each upstream delivery attempt, artifact upload, and indexing. `IngressReceipt` records durable handoff only; `DeliveryReceipt` records one later upstream attempt, including `unknown` delivery outcomes and bounded retry disposition. One successful receipt does not create another.
6. Telemetry correlation has a deliberately closed attribute surface. Patient, waveform, raw packet, endpoint, and credential values are not contract fields.
7. C21 carries Host-owned request ID and expected endpoint revision to one selected Platform Provider. The provider validates correlation but does not create an independent lifecycle ledger or choose another provider.
8. C22 reports installation, VM, service, and capability observations separately. C23 is a delivery plan, while C24 is the only release-proof status source; a pending/unsupported/failed C24 stage never means installation success. A macOS C23 explicitly names either `unsigned` or `developer-id` Installer signature policy; C24 must observe that exact state and the bound package hash, never infer it from a filename or installer exit code.
9. C25 is the immutable signed bootstrap language. It contains no `minimumUpdaterVersion`: the current updater verifies/stages its signed next updater and opaque C26 digest, while only the staged next updater parses C26. Missing/invalid trust evidence is a typed bootstrap failure, not a legacy-parser fallback.
10. C27/C28/C29 keep update admission, bootstrap receipt, per-layer evidence, and Host-owned durable recovery state separate. A C29 journal that decodes but fails its bootstrap/receipt/report cross-field correlations is `invalid`, not an available update. Only complete C28 success evidence advances the Host installation release.
11. C35 keeps Guest build desired input, selected builder identity, compiler input/output receipt, and C34 artifact identity separate. Its additive paired Product inputs (`guestProductProcessSupervisorArtifact` and `guestProductProcessDeploymentConfigurationArtifact`) preserve the original non-product C35 shape. C38, C39, and C44 are separate additive C35 sources; C46 is an additional source only when the selected C44 topology is external; `buildEnvironment` identifies the selected `GuestProductBootstrapArtifactComposer`. Product package composition requires the exact applicable sources without changing the frozen pair rule. C35 emits exactly two storage artifacts: writable RAW `guest-root` and a read-only RAW `guest-product-bootstrap` image whose Guest-visible filesystem is ISO9660. A C35 receipt proves only exact build input/output correlation; it does not prove cloud-init installation, systemd installation, Guest boot, Guest Runtime readiness, topology delivery resolution, or clean-Host package installation.
12. C36 makes the Host public HTTP/WebSocket listener, every target route, request bounds, Host header policy, and replacement client-identity policy explicit. It is Host proxy desired configuration, not a Guest/upstream readiness document.
13. C37 makes Guest Runtime and Recorder Gateway executable paths, listeners, separate durable stores, C44 topology path, optional C46 external delivery-configuration path, an identity-only private credential-material path, and replay limits explicit to the Guest Product process supervisor. C37 does not own a delivery endpoint or select a topology; the Supervisor resolves complete packet delivery and Archive indexed-library adapter inputs from C37/C44/C46 before it plans process arguments. It is Guest desired process configuration, not a Guest artifact inclusion, child-process start, Recorder delivery, archive export, or upstream-health fact.
14. C38 makes the systemd unit name, Supervisor/C37 invocation paths, restart mode/delay, and install target explicit. It is Guest service-manager desired configuration, not a systemd installed/enabled/running observation or child-process readiness fact.
15. C39 `GuestProductBootstrapConfiguration` makes the NoCloud bootstrap identity, Guest-visible ISO9660 filesystem, every Guest Product payload destination including the C44 topology document and, only for external topology, the C46 delivery configuration document, required Recorder Gateway archive paths, systemd unit path, enabled-unit link path, and link target explicit. C40 is the derived plan delivered to the selected `GuestProductBootstrapVolumeComposer`, which creates a read-only RAW storage image containing the `CIDATA` filesystem. C39/C40 do not say cloud-init installed the payload, systemd observed the service, topology delivery was resolved, or the Guest booted.

16. `--extend-baseline` is only for additive v1 contracts after compatibility
passes. `--replace-baseline-for-unreleased-contracts` is a deliberately named,
separate authority for an intentionally unreleased contract redesign. It must
not be used after a v1 artifact has external consumers; that case requires a
new versioned contract and migration.
17. C41 keeps Host build-machine source selection outside C35. Its declaration names every selected source and one new assembled input root; its receipt records C41 declaration, C35 command, builder, and input byte identities without retaining source absolute paths. C41 success is neither C35 compilation, Guest boot, systemd startup, nor package installation evidence.
18. C42 keeps a release-approved raw Guest Linux source disk outside both C41 and C35. Its declaration names one source image identity, either a whole-disk ext4 filesystem or one explicit partitioned-disk ext4 filesystem, and each kernel/initial-ramdisk source as either an exact Guest path **or** a separately identified external artifact. It never guesses between these two sources. A QCOW2 source must first be converted through C73; C42 verifies the resulting raw identity against that receipt rather than treating the QCOW2 URL as the raw file's identity. Its receipt records only immutable input/output identities, not a build-machine path. C42 success is neither C35 compilation, Guest boot, systemd startup, nor package installation evidence.
19. C43 accepts only the identity-verified C42 whole-disk ext4 root-storage output and copies it into one explicitly declared MBR root partition. Its declaration and receipt make the C42 receipt correlation, partition table, Guest disk/partition paths, sector size, and target raw-storage identity explicit. C43 success is neither C40 bootstrap-volume composition, Guest boot, C35 compilation, nor package installation evidence.
20. C32 `LinuxBootResources.guestRootDevicePath` makes the C43-published Guest root partition explicit in the Host boot deployment. The matching kernel `root=` argument is validated as the same value; Host disk-image paths never imply a Guest root device.
21. C44 is the Guest Product release author's single desired VitalServer placement declaration. `bundled-vitalserver` requires an explicit service artifact, process identity, Guest-loopback delivery listener, and state directory; `external-vitalserver` requires both the C16 external integration reference and a deployment-owned external delivery-configuration reference. It carries no endpoint/credential material and no availability, process, or delivery fact. C41, C35, C39, and C40 preserve and install C44 before package publication; for external topology they must preserve the referenced C46 as well. C37 activation must consume an explicit delivery-resolution result before a bundled or external data plane can be claimed.
22. C46 is external deployment-administrator desired configuration, not a network observation. For a C44 external topology, C41/C35/C39/C40 preserve and install its exact non-secret source at the C37-declared Guest path. It binds one C44-selected C16 reference to explicit Socket.IO packet-delivery and indexed-library archive endpoints, distinct provider identities, timeouts, and a C51 credential reference. The Supervisor rejects missing, unreadable, invalid, mismatched, or Guest-loopback C46 input; it does not infer an endpoint or select a bundled fallback.
23. C47 makes one macOS product-package release build reproducible without moving C41/C35/package-adapter ownership into a generic script. Its declaration names C23 selection, C41/C35 execution destinations/times, Host artifacts including the selected macOS operator application bundle, deployment documents, separate PKG and VM-supervisor signing inputs, package/verification executables, and a new receipt destination. It derives Guest package sources from C41 and verifies them against actual C35 output. Its receipt retains declaration/C41/C35/C34/PKG identities without build-machine source paths. C47 build success is not package signing acceptance, clean-Host installation, service registration, Guest boot/readiness, update, rollback, uninstall, or C24 proof.
24. C48 is the release-owned immutable Host product slot contract. It declares the release catalog, release root, `current` activation link, service-definition hashes, the stable packaged Runtime Console C53 path/hash, and—on macOS—the fixed `/Applications/VitalServer Runtime Platform.app` path, entrypoint, and bundle-tree identity separately from persistent data. It carries file identities rather than inferring a release from a receipt, filename, or leftover directory.
25. C49 is the Host Installation Manager's observation only. It carries both the explicit C50 journal and receipt paths and, on macOS, the C48-declared operator application bundle state. Receipt absence, a decoded historical `blocked` receipt-only footprint, arbitrary receipt residue, a stale release catalog or slot, an absent, unreadable, or diverged macOS application bundle, an unreadable or diverged service definition, and an existing mutable store have different states; none can become a clean-install success by fallback. Only the narrowly proved historical receipt-only state can enter the explicit C50 migration transition.
26. C50 gives the Host Installation Manager a durable **install** command/journal/receipt language: `preflight`, `quiesce-services`, `activate-release`, `finalize-services`, and `recover-installation`. Quiescence first records a durable `services-quiescing` intent, so partial service effects remain recoverable rather than hidden. A direct version-changing package install is blocked at preflight; a same-release repair is separately admitted. Package scripts invoke the manager but do not own this policy or launchd effects.
27. C51 is Guest-local private secret material for the C46 indexed-library credential reference. It is delivered by a dedicated secret owner at the C37-declared private path with restrictive filesystem permissions. It has no source example and is forbidden from C35/C39 package inputs, operation state, receipts, telemetry, API responses, and ordinary logs. A missing, unreadable, wrongly permissioned, invalid, or reference-mismatched C51 prevents only the indexed-library archive effect; it never prevents Guest Runtime boot or becomes an anonymous/default credential.
28. C52 is the Host Agent-published, public local-control descriptor. C33 owns the selected Unix peer-user or Windows pipe-ACL authorization policy; C52 contains only the exact local transport and address after that listener is ready. Desktop Console and `platformctl` may read C52, but they must not read C33, infer a port, open a remote address, or treat descriptor absence as a usable local endpoint.
29. C53 is the Host-installation-owned bootstrap document for a packaged Runtime Console launcher. It declares its exact installed path and the expected C52 descriptor path, and nothing more. The launcher passes the C53 path to the desktop shell explicitly; it must not read C33, derive a port or install layout, or replace an absent C52 with a loopback or remote endpoint.
30. C54 is the Host Installation Manager-owned removal lifecycle. Its request must state either `preserve-mutable-data` or `purge-all-product-data`; neither a package-manager uninstall nor a missing path supplies that choice. Before deleting anything it blocks unreadable paths, a diverged service definition, immutable release, or macOS operator application, an active other release, and unfinished installation work. It journals admitted destructive phases, quiesces only C48-declared services, removes only matching C48 resources—including the C48-proved macOS application bundle when present—forgets the declared package receipt, and re-observes C49. Preserve mode writes a durable C54 receipt; purge mode returns the receipt to the invoking console and intentionally leaves no in-product receipt or journal.
31. C55 is one C26-declared layer executor's typed outcome. The executor receives only the staged updater's fixed apply/rollback protocol and writes C55; process exit, output, and logs are transport facts, not a layer result. The staged updater alone correlates C55 into C28.
32. C56 names the Host update handoff supervisor's C31 queue, staging root, C28/C55 evidence roots, C52 descriptor, and timeouts explicitly. C57 is its immutable attempt receipt. `completion-submitted` proves only correlated C27 submission; C29 remains the Host-owned settlement source and no C57 state is update success. C58 is the release-process-owned public-key trust store used by C25 verification; it never contains signing material, and its absence or invalidity remains an explicit bootstrap failure.
33. C60 projects only C51 availability and an immediate private-write outcome through the OS-authorized C52 local-administration facade. The C51 request body is accepted only at that named local route; its values never appear in C60, an operation, a receipt, a package artifact, telemetry, or ordinary logs. A missing C51 is observable and blocks a later archive effect, but does not stop Guest Runtime boot.
34. C61 is the immutable, release-owned C26 desired input for the Host-side Guest Product layer effect executor. It fixes the one C32 Host-loopback-to-C59 path and explicit apply/rollback release transition. The staged Host updater verifies its bytes but never decodes it; C59 remains the sole owner of Guest release staging, activation, rollback, and operation state.
35. C62 is the selected Windows Hyper-V or Linux KVM/libvirt Host deployment input for one amd64 Guest machine. It names the exact C65 manifest file and separately names the two raw files by C65's fixed `guest-root` and `guest-product-bootstrap` roles. The provider verifies the manifest's file identity, its decoded C65 role/format/size/hash values, and both source-file identities before it creates mutable runtime disks. C62 keeps provider-specific firmware/network tools and separately owned mutable native runtime disks explicit. It does not claim that an image was built, a VM was defined, the Guest booted, or its control endpoint is ready.
36. C63 is the selected native Platform Provider's durable receipt after the exact C62 machine and runtime storage definition succeeds. It records the verified C65 artifact-set identity and manifest identity in addition to both raw source identities. It is the sole authority for C62's explicit retained-storage reuse policy; missing, unreadable, mismatched, or partial C63/resources reject a new provision attempt. C63 is not Host operation state, Guest readiness, or C24 installation proof.
37. C64 is the Guest Bundled Upstream Image-set Manager's configuration, update command, and durable operation language. It separates `unprovisioned` from an explicit active image-set, stages a verified image-set archive, invokes only the declared Guest container engine, and records the result durably. A Host C55 effect executor can submit the archive through a declared C32 Host-loopback-to-virtio bridge, but it never reads/writes C64 state or runs the container engine itself.
38. C65 is the Guest image compiler's immutable `amd64` UEFI disk and separate NoCloud bootstrap-volume manifest. It is the package/provisioning identity contract for Windows Hyper-V and Linux KVM/libvirt. C62 must verify it before native conversion and C63 retains its verified identity; it does not claim that either platform has booted the disk, completed cloud-init, or started the Guest Product.
39. C66 is the immutable, release-owned C26 desired input for the Host-side bundled-Upstream image-set effect. It fixes the one C32 Host-loopback-to-C64 path and explicit apply/rollback image-set compare-and-swap transitions. C64 remains the sole owner of Guest image-set archive staging, container-engine invocation, active image-set state, and operation state.
40. C67 is the immutable, release-owned C26 desired input for one installed Host Platform release effect. It fixes the platform-specific stable Host Installation Manager executable, active current-slot C48 manifest path, and compare-and-swap source/target release identity. C68 state and candidate staging belong to that active C48's Installation Manager store; a target archive never selects its own owner path. C67 is not a generic command hook, package-manager hook, or effect result. The staged updater verifies its bytes but does not decode the Host transition.
41. C68 is the Host Installation Manager-owned staged Host Platform update, durable operation, and explicit recovery language. The manager verifies the rigid release archive/C48 target, proves the active C48 bytes, refuses a changed service or mutable-store topology, records service-quiescing/publishing/activation boundaries, atomically changes `current`, and re-registers target services. Failed/unavailable operations retain their last durable state. An operator may request only `reconcile-current-release` after a service-affecting boundary; it re-proves the actual `current` C48 and reconciles that release without replaying an archive or guessing a rollback. Its receipt is distinct from the failed operation. Only a correlated terminal update `succeeded` result can become C55 success.
42. C71 is the Runtime Console packager-owned standalone artifact receipt. It identifies one macOS DMG, Windows NSIS executable, or Linux AppImage/DEB by platform, safe file name, SHA-256, and size, and states that the Console consumes C53 v1. It is a package-build result, never evidence that either the Console or Host product is installed. The macOS C47/C48 unified product PKG selects an application bundle directly instead of using C71 as an installer input.
43. C72 is the release-process-owned operator delivery kit for a channel that intentionally distributes a Host installer and a separate C71 Console artifact. It copies their verified bytes into a new immutable kit, correlates the exact C53 bootstrap byte identity, and fixes installation order to Host first, Console second. It does not replace the unified macOS C47/C48 PKG path, and it does not install, update, remove, start, or prove either component.
44. C73 is the Guest Linux source disk materializer's release-build declaration and receipt. It verifies one caller-selected ARM64 QCOW2 source image and converts it through a caller-selected image tool into one identity-recorded raw disk. It does not acquire a Linux image, select a partition, extract C42 boot resources, boot a Guest, or claim package installation.
45. C74 is the release-process-owned review record for one new immutable C24 proof-set candidate. It binds the exact source proof set, reviewed proof fragments, and their evidence identities. It never overwrites a source C24 document, infers evidence from a URI, or creates Host installation state.

## Local verification

Create the root-local virtual environment once, then run all checks:

```sh
make -C runtime-platform bootstrap-contract-tools
make -C runtime-platform check
```

The verifier checks JSON Schema meta-validity, example decode failures, OpenAPI validity, operation transition invariants, and `v1` compatibility against the frozen baseline.

After an additive contract has passed compatibility verification, extend the baseline deliberately:

```sh
make -C runtime-platform contract-extend-baseline
```

This command first rejects any mutation of an already baselined `v1` schema or public operation, then records only the compatible current source as the new reference point. It is not a mechanism for accepting a breaking change.
